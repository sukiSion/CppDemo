1、不要坚持认为声明都应带放在函数的最上面
解决办法：
1) 将声明语句直接放在第一次使用之前
2) 始终初始化一个变量，如int i{}，或最好使用auto。编译器无法从auto i这样的声明中猜出i的类型因此会拒绝程序。反过来说，auto迫使变量初始化
2、不要坚持在一个函数中只保留一条return语句
使用一个以上的return语句可以使代码更容易阅读、也更快
若使用自动返回类型推导返回不同的类型会导致程序异常（参考differentReturnTypes.cpp）
3、不要避免使用异常
反对异常的原因：
1) 异常是低效的
2) 异常会导致泄漏和错误
3) 异常的性能不可预测
4) 异常处理的运行需要太多空间
编译器用来实现异常的两种典型方式：
1) 基于代码的方法，代码与每个try块相关联
即使没有抛出异常，也必须对异常处理堆栈进行薄记处理，因此与错误无关的代码也会变慢
2) 基于数据表的方法，使用编译器生成的静态数据表
没有抛出异常时不会阴图栈或运行期的开销但数据表方法的实现更复杂，且静态数据表可能会变得相当大
使用异常：
1) 明确区分错误的返回和普通的返回
2) 不会被遗忘或忽视
3) 可以系统地使用
4、不要坚持把每个类声明放在独立的源文件中，正确方式是使用命名空间
若为每个类的声明使用一个独立的文件将产生过多的文件进而使你的程序更难管理，编译更慢
5、不要采用两阶段初始化
构造函数的工作：在执行构造函数后应该有一个完整初始化的对象
应该在类的主体中设置对象的默认行为，构造函数只是用来改变默认行为
init成员函数经常会被用来把常见的初始化或验证流程放在一个地方。需要在构造函数后立即调用。虽然遵循了DRY原则（不用在每个构造函数都进行初始化或验证）但却破坏了“对象应该在构造函数调用之后完整初始化”。
从C++11开始可以使用委托构造函数，这意味着可以把通用的初始化和验证逻辑放到一个聪明的构造函数中，而其他的构造函数只是一种包装。
6、不要把所有清理操作放在函数末尾并使用goto exit
请使用资源句柄和RAII（资源获取即初始化）自动管理资源（参考lifecycle.c和lifecycle.cpp）
7、不要使所有数据成员protected
受保护的数据使程序变得复杂且容易出错。如果把受保护的数据放到基类中，就不能孤立地仅根据派生类来继续推理因此破坏了封装。
受保护的数据使类层次结构范围内的一种全局数据。而可变的、共享的状态非常糟糕。
