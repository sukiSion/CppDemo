# 错误的优化
1、不要无故优化
2、不要过早进行优化
3、不要优化并非性能关键的东西
**使用真实数据进行性能测试，并在版本控制下进行测试。每次修改基础架构中的某些东西（如硬件或编译器），都要重新运行这些性能测试。在错误假设的基础上进行大量的优化是一个典型的反模式**

# 错误的假设
1、不要假设复杂的代码一定比简单的块
2、不要假设低级代码一定比高级代码块
3、不要再没有测量的情况下对性能妄下断言
**不建议使用臭名昭著的单例模式，单例模式有很多缺点**
以测量各种单例模式的性能为例子（参考singletonMeyers.cpp和singletonDoubleCheckedLockingPattern.cpp）

# 启用优化
1、设计应当允许优化
尤其适用于移动语义，写算法时适用移动语义而不是拷贝语义自动带来的一些好处：
1) 算法使用低开销的移动操作，而不是高开销的拷贝操作
2) 算法要稳定得多，因为它不需要内存
3) 可将算法用于只能移动的类型，如std::unique_ptr
当在一个需要移动语义的算法中使用一个“只能拷贝”的类型（参考swap.cpp）
**在一个“只能拷贝”的类型上应用移动操作会触发拷贝操作，用移动语义实现算法意味着如果数据类型支持移动语义，那么移动语义会自动生效。如果不支持，则使用拷贝语义作为回退**
2、依赖静态类型系统
1) 写本地代码：一般来说使用就地调用的lambda表达式（而不是函数）来调整std::sort的行为代码会更快
2) 些简单的代码：优化器会搜寻可以被优化的已知模式。
3) 给予编译器额外的提示：比如noexcept（函数不抛出异常），final（虚函数不应该被覆盖）
3、将计算从运行期移至编译期
将一个函数声明为constexpr使其成为一个可在编译器执行的函数。
constexpr函数不能static或thread_local变量，不能使用异常处理，也不能使用goto语句，并且所有变量都必须初始化为字面类型。字面类型本质上是一个内置类型，或是引用，或是字面类型的数组，或是拥有constexpr构造函数的类（参考gcd.cpp）
**constexpr函数可以在运行期使用，也可以在编译期使用，如果要在编译期使用它，其参数必须是常量表达式**
4、以可预测的方式访问内存
std::vector，std::array，std::string使用连续内存块存储元素
std::deque元素没有存储在一个连续内存块中，而是通常存储在一个固定大小的数组中，这些固定大小的数组会在新数组添加到std::deque之前被填满
std::list和std::forward_list是双链接或单向链接的容器，它们都能在两个方向上增长
对以上类型读取和累加所有元素，性能上会存在差别吗？（参考memoryAccess.cpp）
**元素的访问时间是影响整体性能的主要原因，元素的访问时间在很大程度上取决于容器的缓存行**
