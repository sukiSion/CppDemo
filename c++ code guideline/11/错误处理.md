异常安全的基本契约：
1) 不抛出异常，也称为故障透明：即使在异常情况下，也能保证操作成功并满足所有的要求。如果发生异常，则会在内部处理，客户无法观察到。
2) 强异常安全，也称为提交或回滚语义：操作可以失败，但失败的操作保证不会产生任何副作用，因此所有的数据都将保留其原始值
3) 基本异常安全，也成为无泄漏保证：部分执行失败的操作可能会产生副作用，但所有的不变式都会保持，并且没有资源泄漏（包括内存泄漏）。任何存储的数据都包含有效的值，即使它们于异常发生前的值不同
4) 无异常安全：不做任何保证

# 设计
## 通信
1、在设计初期制定错误处理策略
2、不要试图在每个函数中捕获每个异常
3、尽量减少显式的try/catch使用
**软件单元：可以是函数、对象、子系统或整个系统。**

## 不变式
**不变式：对象成员的一种逻辑条件，构造函数必须建立这个条件，这样公开成员函数就可以假设它一定成立。在不变式建立后（通常通过构造函数），对象上的每个成员函数就可以调用了**
1、通过抛出异常来表明函数无法执行其分配的任务
2、围绕不变式来设计错误处理策略
3、让构造函数建立不变式，做不到就抛异常

# 实现
## 该做的事
1、只对错误处理使用异常
2、应使用专门设计的用户定义类型（而非内置类型）作为异常
3、通过引用从层次结构中捕获异常
1) 应该通过const引用来捕获异常；仅在想要修改异常时通过（非const）引用来捕获
2) 如果你要在异常处理器中重新抛出异常e，只需要使用throw而不是throw e。在第二种情况下，e会被复制

# 不该做的事
1、在直接拥有对象时绝不抛异常
最简单的解决方案事摆脱所有权，让C++运行时成为对象的直接所有者
也可以只创建局部对象，或者起码作为局部对象使用的守护对象。C++运行期会处理局部对象，并在必要时释放内存。
2、不要使用异常规则
一个例子：
```cpp
int use(int arg) throw(X , Y){
    // ...
    auto x = f(arg);
    // ...
}
```
这意味着函数use可能会抛X或Y类型的异常。如果由其他异常抛出，那么std::terminate会被调用
**不要使用这种方式**
3、正确排列catch子句的顺序
**通常为从具体到一般来组织异常处理器**

# 如果不能抛出异常
1、如果不能抛出异常，请模仿RAII进行资源管理
**RAII思想：如果你必须照管一项资源，就把这个资源放在一个类中。使用该类的构造函数进行初始化，并使用析构函数来销毁资源。**
2、如果不能抛出异常，考虑快速失败
**如果没有办法从内存耗尽等错误中恢复过来，那就快速失败。如果不能抛出异常那就调用std::abort促使程序异常终止**
3、如果不能抛出异常，请系统地使用错误代码
