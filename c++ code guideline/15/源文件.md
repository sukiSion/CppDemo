# 接口和实现文件
声明接口通常在*.h文件中，定义或实现则在*.cpp文件中
1、如果你的项目还没有采用其他约定，那代码文件使用.cpp后缀，接口文件使用.h后缀
头文件：
1) *.h
2) *.hpp
3) *.hxx
4) *.inl
实现文件：
1) *.cpp
2) *.c
3) *.cc
4) *.cxx
2、.h文件不可含有对象定义或非内联函数定义（.h文件通常用来声明函数）
C++有单一定义原则（ODR）：
1) 一个函数在任何翻译单元中不能有一个以上的定义
2) 一个函数在程序中不能有一个以上的定义
3) 有外部链接的内联函数可以在一个以上的翻译单元中被定义。这些定义必须满足一个要求：它们全部相同
若使用链接器链接一个头文件（定义了非内联函数）和两个实现文件，编译器会抱怨函数有多个定义
3、.cpp文件必须包含定义其接口的.h文件
4、为所有的.h文件使用#include 防护宏
```cpp
#ifndef LIBRARYNAME_FOOBAR_H
#define LIBRARYNAME_FOOBAR_H

#endif
```
需要注意：
1) 给防护宏一个唯一的名字。如果多次使用同一个防护宏名字，可能导致本应包含的头文件被排除在外
2) #pragma 预处理指令不标准，但广泛受到支持。使用# pramga once 可以防止头文件被多次包含
5、避免源文件间的循环依赖（参考a.h、b.h和main.cpp）
可以使用前置声明解决循环依赖，标准库头文件<iosfwd>中有标准输入/输出库的前置声明
6、避免隐含#include进来的名字的依赖
7、头文件应当是自包含的
自包含：头文件不依赖于之前包含的其他头文件

# 命名空间
命名空间为标识符提供作用域。标识符可以是类型、函数或变量的名称
1、（仅）对代码迁移、基础程序库（比如std）或者在局部作用域中使用using namespace指令
using指令隐藏了名称的来源，且破坏了代码的可读性（参考namespaceDirective.cpp和namespaceDirectiveRemoved.cpp）
2、不要在头文件的全局作用域中使用using namespace
头文件全局作用域的using namespace会将名字注入包括该文件的每个文件中，这回产生不好的后果
1) 当你使用这个头文件时，你无法撤销其中的using指令
2) 名字冲突可能性急剧增加
3) 对被包含的namespace的改变可能会破坏你的编译，比如其中引入了一个新的名字
3、使用namespace表示逻辑结构
```cpp
std
std::chrono
std::literals
std::literals::chrono_literals
std::filesystem
std::placeholders
std::view // C++20
```
4、不要再头文件中使用无名（匿名）命名空间
5、为所有的内部/不导出的实体使用无名（匿名）命名空间
**无名namespace使用内部链接。内部链接意味着无名namespace内的名称只能在当前的翻译单元内引用而不能导出。**
在头文件中使用namespace时，每个翻译单元都定义了这个无名namespace的唯一实例。头文件的无名namespace会导致：
1) 所产生可执行文件大小会膨胀
2) 无名namespace中的任何声明都是指每个翻译单元中的不同实体，这可能不是所期望的行为
无名namespace的用法类似于C语言里使用的static关键字
```cpp
namespace {int i1;}
static int i2;
```
